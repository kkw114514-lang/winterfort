# 开发准则 v1（项目规范 · 人与 AI 共同遵守）

> 本项目模式：**你（设计师）定方向并验收，AI（Codex）负责实现**。
> 本文是全项目的"行为底线 + 设计准则"，与《编程架构》《局内战斗设计》等配套；有冲突以设计文档为准。
> 建议把"第三部分（AI 施工军规）"同时放进项目根的 `AGENTS.md`，让 Codex 每次自动遵守。

---

## 第一部分 · 核心设计准则（架构层面）

1. **三层分离**：数据、逻辑（算账）、表现（显示）永远分开。改 UI 不该动到算账，调数值不该动到代码。每写一块先问自己：这是数据、逻辑、还是显示？

2. **数据驱动**：能做成"数据"的绝不写成"代码"。卡牌、精灵、敌人都是数据，代码只负责"读数据、按规则执行"。这是让一个不写代码的人也能做大体量卡牌游戏的根本。

3. **小积木可组合**：不为单张卡写专属逻辑，而是做好"造成伤害""施加灼伤"等通用小积木，让卡由积木拼装。积木越小越通用，新内容越便宜。

4. **单一信息源**：同一份数据只存一处（如能量只存在战斗状态里），显示层去"问"它、不另存一份。杜绝"界面与实际不一致"的 bug。

5. **渐进式 / 垂直切片**：先做"能从头玩到尾的最小一条"，跑通再加厚。每一步都要"能跑、能验证"。不憋大招、早暴露设计问题。

6. **留接缝、不留占位**：为以后可能加的系统**留好接口/钩子**，但**不实现**它、也不写"以后要删的占位代码"。设计对扩展开放，代码只写当下需要的。

---

## 第二部分 · 数值与可调性（平衡友好）

7. **卡牌数值一律不写死**：费用、威力、状态层数/等级、力量/护盾数值等，**全部放数据（Excel → 导出），绝不硬编码在逻辑里**。改数值 = 改表格，不碰代码、不用 AI 重写。

8. **所有"平衡数字"集中可调**：不止卡牌——能量公式里的常量、抽牌公式、稀有度权重（如 60/37/3）、敌人数值等，都做成**集中的配置常量/数据表**，放统一的地方，杜绝散落各处的"魔法数字"。做平衡时一处即可调。

9. **代码只读数值、执行规则；数值本身是数据。**

---

## 第三部分 · AI 施工军规（实现层面 · 建议同步进 AGENTS.md）

1. **先查后写**：遇到不确定的接口/用法，先查官方文档与说明，**绝不靠猜写接口**。查不到就明说，不臆造。

2. **先懂再干**：需求或逻辑没弄明白，**先问清楚再动手**，不稀里糊涂开工。

3. **拿不准就确认**：业务规则不清时一定向人确认，**不自己脑补规则**。（规则以项目设计文档为准。）

4. **复用优先**：有现成的代码/接口/小积木就直接复用，**不重复造轮子**。

5. **写完必自测**：每写完一块都自己运行验证（play_scene / 截图 / 打印日志 / 断言），**不跳过验证就交活**；并向人说明验证结果。

6. **守规范、不乱动**：遵守项目目录与架构规范，**不擅自重构、拆改、挪动现有结构**；改动前说明影响范围。

7. **不懂就说不懂**：不会就直说，**不懂装懂瞎写**。说"不确定"不丢人，乱写才是坑。

8. **改动要谨慎**：重构与修改要小步、可回退，**不脑子一热盲目大改**；优先在不破坏现有功能的前提下增量修改。

---

## 第四部分 · 你与 AI 的分工

- **你 = 设计师 + 审查官**：定"做什么、对不对"，验收结果。看不懂 AI 的方案/操作就让它解释，**签字前看懂大概，不盲签**。
- **AI = 施工队**：定"怎么写"，按规格实现并自检。
- **协作铁律**：小步、给清规格、给验收标准；设计文档是唯一真理，喂给 AI、变更同步更新。

---

## 第五部分 · 协作与推进方式

1. **步骤尽量细化**：把每个功能拆成"可独立验证、可单独 commit"的最小步。宁可多拆几步，也不要一口气做一大坨——大块最容易翻车、难回退、难定位。每一小步都要：能跑、能验证、做完存档。
2. **多询问**：需求、边界、业务规则不清楚时，先问清再动手，不臆测、不脑补。
3. **多提建设性意见**：不只被动执行——主动指出更优方案、潜在坑、可简化或可复用之处，以及"现在做 vs 以后做"的取舍建议。
4. **存档三位一体（硬性 · 存档前必过）**：任何改动在 `git commit / 合并` 前，必须**三方一致**才放行——
   - **① Claude（架构师）读"真实提交代码"复核通过**：以实际代码为准，**绝不以 Codex 的报告/日志为准**；设备挂载缓存不可信时，用 `git show HEAD:<路径>`（PowerShell）绕开缓存读真码。
   - **② Codex 报告 / 自测通过**：其实现说明与自测结果。
   - **③ 设计师亲手实际操作验证通过**：真机跑一场、亲眼确认行为对。
   三处只要有一处对不上，就**先查清、不存档**（例如"代码 grep 与亲测矛盾"时，必须定位到底哪一方是旧的/错的，才继续）。
   > 立此条的教训：一次 Codex 报告"已修"、Claude 读到的却是旧码（实为设备挂载缓存喂了旧文件）、最终靠设计师亲手一玩才定案——三方交叉才能防"单方误判"。
